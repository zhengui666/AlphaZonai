# Native strategy delivery

AlphaZonai uses Pi Durable to turn factor research into a complete native
NautilusTrader strategy, not to select a fixed strategy family. It delivers the
same source and configuration the selected Nautilus backtest instance evaluated.
Backtest and deployment instances have separate configuration and may both be
remote.

## User workflow

1. Start research through the CLI and wait for a completed run with usable
   elite candidates. You can set an optional research direction at admission.
2. Use the CLI to choose a configured backtest target and a later UTC date
   range. Add a free-text strategy brief if useful. The model receives the
   original research direction and selected factor evidence.
3. The build inherits the run's connected provider (OpenAI API or ChatGPT via
   Pi's Codex OAuth), model, reasoning intensity and service tier. Defaults
   changed after the run do not alter a build. Pi Durable generates a standalone native Python module, its strategy class,
   config class and configuration values. The code can implement any native
   strategy compatible with the available Nautilus data and dependencies. There
   is no compiled-in menu of strategies, indicators, long-only assumptions,
   or presets in strategy delivery.
4. The backtest target runs the requested module in an isolated NautilusTrader
   engine. Inspect the technical receipt and the exact source and configuration
   in the downloadable package.
5. Use the CLI to push an inactive package to an independently configured deployment target. The receiver checks that the source and config
   match the receipt, compiles syntax without importing it, and writes the
   native package atomically. The verified receipt says which instance staged
   it. It does not start a trading node or place any orders.
6. Activation is a separate operator action in the target Nautilus setup. Review
   source, configure live adapters/account/risk separately, then load the
   importable configuration in the existing Nautilus instance. A generated
   package is suitable for review and loading, not guaranteed profitable or
   approved for unattended live operation.

The source is generated by the model; it is not a generic renderer that
translates arbitrary historical factor programs automatically. Model output
may use the studied factors or implement a different proposition. Review the
source and holdout evidence to understand what was actually tested.

## Profiles and entry points

Use **Settings → NautilusTrader settings** to save the strategy token and
targets. Supply the same token to authorized CLI commands with
`--token-file FILE`. Run on a private interface, SSH forward, or authenticated
TLS proxy. Each target specifies its allowed operations and the receiver on
which they run. To apply the following object from a file, use
`alphazonai settings set --section nautilus --file targets.json`.

```json
{
  "targets": [
    {"id":"history","label":"Historical runner","kind":"local","roles":["backtest"],"profile":"/etc/alpha/history.json"},
    {"id":"runtime","label":"Remote strategy host","kind":"ssh","roles":["deploy"],"alias":"alpha-runtime","sshConfig":"/etc/alpha/ssh/config"}
  ]
}
```

A target can have both roles. An optional `marketContext` string on the
backtest registry entry describes available data streams and venue details for
the model, without sharing filesystem paths or credentials. For a remote target, pin the host key in the
client SSH config, and create a dedicated identity scoped to this receiver.
The private key stays on the AlphaZonai host. On the remote side, configure
OpenSSH to use a forced command with no interactive shell, TTY, agent or
port forwarding, for example:

```text
/path/to/python /path/to/strategy_receiver.py --profile /etc/alpha/receiver.json
```

Install `quant/strategy_receiver.py` and `quant/strategy_backtest.py` from the
same AlphaZonai release. Use NautilusTrader 1.231.0 in the receiver interpreter.
The Python environment should contain only runtime libraries, never secrets.
A local target uses the Python interpreter set in **NautilusTrader settings**,
read-only Catalog access and the same receiver. A remote backtest additionally needs Bubblewrap and a host policy
that allows the runtime to open isolated user/PID/network namespaces.
A stage-only target needs no Bubblewrap, Catalog, or market/exchange keys.
Capabilities are checked on both the sender and the receiver.

### Backtest profile

The `run` field is an operator-provided native Nautilus `BacktestRunConfig`.
Populate its data/venues and latency, fee or slippage settings as needed.
This server does not provide strategy presets or fabricate prices. The user
selects a later time window. The receiver substitutes its read-only catalog
mount, exclusive end and generated native strategy configuration. Do not
put account credentials or custom execution clients in the backtest profile.

```json
{
  "instance":"history",
  "allow":["backtest"],
  "catalog":"/catalog",
  "run":{
    "chunk_size":100000,
    "venues":[{"name":"HYPERLIQUID","account_type":"MARGIN","oms_type":"NETTING","starting_balances":["10000 USDC"]}],
    "data":[{"data_cls":"nautilus_trader.model.data:Bar","bar_types":["ASSET-PERP.HYPERLIQUID-1-MINUTE-LAST-EXTERNAL"]}]
  }
}
```

Replace the illustrative, neutral instrument identifier and settings with
your Nautilus catalog's native IDs. For other data types or multiple markets,
provide their native data configurations. Source and config must match those
available streams. Credentials never enter the backtest sandbox. It uses an
isolated network namespace, a read-only Catalog, no writable host mount, a
bounded scratch area and a bounded result pipe. The sandbox cannot make a
native same-process strategy mathematically trustworthy: malicious Python
could distort its own measurements. Review code and verify behavioral and
risk claims before activation. No paper- or live-account requests happen here.

### Deployment profile and activation

```json
{"instance":"production-runtime","allow":["stage"],"staging_dir":"/srv/alpha-packages"}
```

Create a receiver-owned staging directory, distinct from any auto-load or
auto-restart directory. The receiver writes a directory named by the package
UUID with `alpha_strategy_<uuid>.py`, `importable-strategy.json` and
`strategy-package.json`. The unique module name lets a native instance load
more than one staged strategy without module collisions. Push does not
import or execute the source; only syntax and receipt checks occur.
At the intended Nautilus startup, explicitly add the staged directory to
that process's Python import path and add the config to its native
`ImportableStrategyConfig` list. Broker credentials are configured on the
existing live node and never travel through AlphaZonai.

## Durable operations, atomicity and protocol

- `GET /api/strategy-targets` exposes only permitted IDs, labels and roles.
- `POST /api/runs/:researchId/strategies` with Bearer token sends
  `{"action":"build","id":UUID,"target":backtestId,"start":"YYYY-MM-DD","end":"YYYY-MM-DD","brief":"optional instructions"}`
  or `{"action":"push","id":strategyId,"target":deploymentId}`. Reuse the
  same UUID on a retry of the same build. A settings mismatch is rejected.
- `GET /api/runs/:researchId/strategies?download=:strategyId` downloads the
  validated bundle; the existing run state and SSE expose persisted stage
  outcomes. The model does not choose the deployment target or initiate push.
- Pi Durable checkpoints generated source and configuration before native
  backtesting. Backtest is repeatable after interruption; only a complete
  receipt with actual simulated fills can be staged. This is a technical
  criterion, not a profitability threshold. Use separate risk evaluation.
- Receiver protocol v2 is one JSON request on stdin and receipt on stdout.
  The sender checks Nautilus version, operation, UUID, exact source and config.
  Stage compares them again and fails before disk publication if modified.
  Stage uses an atomic same-filesystem rename. The same UUID and same bytes
  can be retried; different content is never overwritten. The receiver is a
  user-controlled trusted endpoint, not an external attestation service.
- No unpublished strategy is automatically activated, and no account,
  leverage, adapter, position or live order state is modified.

## Verification

A CI round trip takes an unrestricted generated-style Nautilus Python module,
loads it in the isolated native backtest on a later data window, asserts native
simulated fills, then stages identical source and config in a separate target.
It checks altered-source rejection and repeated stage. A loopback OpenSSH
test exercises distinct target identities/forced commands through the actual
TypeScript transport. Neither test connects to a market or invokes a paid
model. A real-host rollout still needs its own receiver and compatibility
checks.
